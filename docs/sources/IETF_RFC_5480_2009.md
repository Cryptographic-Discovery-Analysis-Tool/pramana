# RFC 5480 — Elliptic Curve Cryptography Subject Public Key Information

- **Publisher:** IETF (Internet Engineering Task Force); RFC Editor
- **Authors:** S. Turner (IECA), D. Brown (Certicom), K. Yiu (Microsoft), R. Housley (Vigil Security), T. Polk (NIST)
- **Date:** March 2009
- **Category:** Standards Track (Proposed Standard)
- **DOI:** 10.17487/RFC5480
- **URL:** https://www.rfc-editor.org/rfc/rfc5480.txt (info page: https://www.rfc-editor.org/info/rfc5480/)
- **Retrieved:** 2026-09-28, plain-text RFC (via web fetch)
- **Why vendored:** `cryptography`/OpenSSL report an EC key's curve using the
  ANSI X9.62/SECG wire name (`secp256r1`, `secp384r1`, `secp521r1`, ...), but
  `data/crypto_families.yaml`'s ledger-cited families use the NIST FIPS 186
  names (`P-256`, `P-384`, `P-521`). This RFC states the naming-identity
  correspondence directly (it is the document that defines those curve OIDs
  for use in X.509 SubjectPublicKeyInfo).

## Section 2.1.1.1 — Named Curve, correspondence note

Exact sentence:

- "Note that [FIPS186-3] refers to secp192r1 as P-192, secp224r1 as P-224,
  secp256r1 as P-256, secp384r1 as P-384, and secp521r1 as P-521."

This is a naming-identity statement only (two spellings of the same curve),
not a security claim -- used here the same way
`data/crypto_families.yaml`'s existing `secp256r1 -> P-256` /
`prime256v1 -> P-256` rows are (previously cited only to
`Pramana_Ledger_Spec.md` §6, which names the curve `P-256` but does not
itself state the `secp256r1` wire-spelling correspondence as a fact from an
external standard).

## Section 2.1.1.1 — OID values (for reference; not what the alias rows cite)

```
secp256r1 OBJECT IDENTIFIER ::= {
  iso(1) member-body(2) us(840) ansi-X9-62(10045) curves(3)
  prime(1) 7 }

secp384r1 OBJECT IDENTIFIER ::= {
  iso(1) identified-organization(3) certicom(132) curve(0) 34 }

secp521r1 OBJECT IDENTIFIER ::= {
  iso(1) identified-organization(3) certicom(132) curve(0) 35 }
```
